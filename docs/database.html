A small schema with a serious security surface.

Eleven core SQL Server tables, eleven restricted views, fourteen canonical procedures, five database roles, and a certificate-backed encryption hierarchy. A seeded SQLite database supports development when SQL Server is unavailable.

Secure projections

Eleven views that narrow the record.

Views express public projections, own-row access, assignment scope, and admin summaries. They are not a complete substitute for per-user database principals.

Views use SYSTEM_USER to identify the principal.The default demo connects as SA, so this identity is the same for every application user. Application-level own-row checks remain essential; production requires per-user database principals.

Procedures

Policy that lives in T-SQL.

The canonical procedure script mirrors the application’s MLS, inference, flow, encryption, login, and role-workflow decisions.

Authentication and MLS

sp_UserLogin sp_MLSReadCheck sp_MLSWriteCheck sp_MLSAccessCheck

Credential verification, account lockout, login audit, and structured read/write decisions.

Inference and flow

sp_GetCourseStatistics sp_CheckDataFlow sp_CheckExportAllowed

Reject undersized aggregates, blocked downflow, and classified exports.

Encryption and grades

sp_EncryptData sp_DecryptData sp_InsertGrade

AES-256 key operations and a combined MLS-check, encrypt, and insert path.

Role workflow and users

sp_SubmitRoleRequest sp_GetPendingRoleRequests sp_ProcessRoleRequest sp_CreateUser

Submit, list, approve or deny privilege changes, and create users with hashes and audit.

Legacy compatibility procedures live in sql/sqlserver_procedures_fixed.sql. The canonical script is sql/sqlserver_procedures.sql.

DEMO ONLY

Public credentials, deliberately

These accounts exist so a reviewer can reproduce every role boundary immediately. They are not a credential-management pattern and must never protect real records.

Never reuse the demo SA password, app credentials, backup, or sample records outside a local classroom environment.
