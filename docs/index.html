Academic records, secured by design.

SRMS is a role-aware student information system built around five database-security models: RBAC, Bell–LaPadula multilevel security, inference control, flow control, and encryption. A working course project — and an honest reference for what each layer can and cannot guarantee.

The problem

Hiding a menu is not access control.

A conventional CRUD interface can authenticate a person and remove a button, yet still leave the underlying records exposed to a different query, a small aggregate, or an export path. SRMS treats those as security decisions that must be made explicitly.

The project asks five review questions and keeps the answer close to the code: role and row ownership, read/write clearance, aggregate disclosure, data movement, and protection at rest.

Course project, not production software.The code paths are real, but the deployment ships public demo credentials, an SA connection path, and no automated security regression suite. The limitations are documented rather than hidden.

REVIEW MODEL

Five decisions, one request

  • May this role perform this operation?
  • Does clearance allow this direction?
  • Does the result set expose an individual?
  • May this data move to that context?
  • Can the action and outcome be audited?

Role boundaries

Access follows the role — and the row.

Clearance is only one input. Assignment, ownership, and publication filters determine which records a role can actually reach.

Admin

Clearance 4 · Top Secret

Full security and records administration. The role is trusted for MLS write-down by an explicit policy exception, not by accident.

  • RecordsCRUD across student, instructor, course, grade, attendance, and user tables.
  • GovernanceReview, approve, or deny role requests; inspect the audit log.
  • SecuritySee all classification levels and security-model status.
  • FlowTop Secret copy and export actions remain blocked by the action policy.

Instructor

Clearance 3 · Secret

Academic decisions within assigned courses. Profile access is read-only; grade writes require course ownership.

  • GradesRead, insert, and update for assigned courses; delete is denied.
  • StudentsRead students associated with assigned courses.
  • AttendanceRead assigned-course attendance; writes belong to the TA delegation.
  • RequestsSubmit and view own role requests.

Teaching Assistant

Clearance 2 · Confidential

A deliberately narrow delegation: attendance for assigned courses, and no grade access in either the application matrix or SQL Server role.

  • AttendanceRead, insert, and update assigned-course rows; delete is denied.
  • StudentsRead assigned students only.
  • GradesNo access.
  • RequestsSubmit and view own role requests.

Student

Clearance 1 · Unclassified

Own-record access through dedicated views. The own-profile exception is an explicit ownership policy on top of a Confidential classification.

  • ProfileRead own linked profile through vw_StudentOwnProfile.
  • GradesRead own published grades only; encrypted values are not exposed.
  • AttendanceRead own attendance rows.
  • RequestsSubmit and track a TA or Instructor role request.

Guest

Clearance 0 · Public

Public course discovery only. Guest entry is a role, not an anonymous bypass of the database policy.

  • CoursesRead the public course projection only.
  • StudentsNo access.
  • GradesNo access.
  • RequestsCannot submit a role request.

A documented policy conflict, not a hidden bypass.Attendance is classified Secret while the TA clearance is Confidential. Assignment-scoped views express the delegated duty, but a pure MLS check would deny it. The project records this tension for an explicit future policy decision.
