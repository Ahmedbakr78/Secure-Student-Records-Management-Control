Straight answers

What SRMS is — and what it is not.

Short answers to the questions a reviewer, instructor, or future contributor is most likely to ask.

Course project Not production-ready Residual risk documented
Is this safe to use for real student records?

No. SRMS is an educational reference implementation. It ships public demo credentials, an SA application path, hard-coded connection settings, simulated second factors, a mutable audit table, and no automated security regression suite. Use it only with disposable demo data.

Why publish usernames and passwords?

The published accounts let a reviewer reproduce every role boundary immediately: Admin, Instructor, TA, Student, and Guest. They are deliberately demo-only. They must never be reused outside a local classroom environment and must never protect real records.

Does SRMS really enforce all five security models everywhere?

No — and the project does not claim that. The models have named implementations and database mirrors, but some GUI paths call models directly, the Python matrix and SQL Server roles can drift, and enforcement is most consistent where data crosses from a dashboard into a model. The limitations are stated in the security models page and the threat model.

How can a TA edit attendance if attendance is Secret and the TA is Confidential?

This is a known policy conflict. The TA has a global clearance of 2 (Confidential), while attendance is classified 3 (Secret). Assignment-scoped views and RBAC express the delegated attendance duty, but a pure Bell–LaPadula no-read-up check would deny it. The project documents the tension instead of silently elevating the TA. A future policy must either raise the clearance, lower the classification, or introduce a formal delegated-access rule.

Should I use SQL Server or SQLite?

SQL Server is the canonical security path: database roles, secure views, fourteen procedures, and a certificate-backed AES-256 hierarchy. SQLite is a development and UI-review fallback with no stored procedures, database roles, secure views, or SQL Server encryption hierarchy. Application-level checks still run, but the security properties are not equivalent.

Why are there two encryption schemes?

The SQL Server path demonstrates a database master key, certificate, and AES-256 symmetric key. The application path demonstrates Fernet authenticated encryption with a PBKDF2-derived key. They do not share a key lifecycle. Password hashing also differs: bcrypt on the model/SQLite path and SHA-256 + salt on the SQL Server path. These are documented limitations, not a unified production key-management design.

Is the Flask viewer part of the security boundary?

No. It is a read-only, localhost-only database inspector with allow-listed tables. It has no application authentication of its own. Do not expose port 5000 or treat the viewer as a secure application surface.

Does the audit log make the system tamper-evident?

No. AUDIT_LOG records authentication, access, writes, and workflow events, and the admin dashboard exposes them. But it is a normal table. An administrator with direct database access can alter it. It is a detective control, not an append-only or cryptographically tamper-evident store.

How does the role-upgrade workflow work?

A user submits a request for TA or Instructor with a reason. The request is stored as Pending. An admin reviews it, then approves or denies it with comments. Approval updates the role and clearance and writes an audit event. Duplicate or invalid requests are rejected. The full sequence is in guide 16.

Are there automated tests?

Not for the security controls. There is a substantial manual matrix and a verification script that checks imports, connectivity, schema presence, managers, authentication, and role-request support. Automated unit, integration, and UI tests are roadmap items. A static documentation build can validate links, HTML, YAML, and assets without running the app.

Why is the documentation website static?

It needs no runtime, database, or build service, which makes review simple and hosting durable. The trade-off is that content must be kept in sync manually with the Markdown guides and source code.

Why was the project renamed?

The former repository name was long and described the original coursework framing. The new name, Secure Student Records Management Control, keeps the established short name SRMS while presenting the project as a current reference implementation. The original remote repository was left untouched.

What is the demo dataset?

The two seeds are different. The SQL Server sample has 8 users, 4 instructors, 8 students, 5 courses, 10 grades, and 15 attendance records. The SQLite database has 11 users, 2 instructors, 5 students, 3 courses, 12 grades, and 50 attendance records. Counts are backend-specific and should not be combined.

Where should I start?

For the architecture, read the system map. For the controls, read security models. To run it, follow setup. To evaluate it, use the test matrix and the threat model.
