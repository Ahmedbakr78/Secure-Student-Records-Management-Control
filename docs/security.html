Policy and enforcement

Five controls that answer different questions.

Authorization is not one check. SRMS separates role permission, clearance, aggregate inference, data movement, and encryption — then records the outcome. This page maps each model to its code path and its limits.

RBAC Bell–LaPadula Inference control Flow control Encryption
01 · AUTHORIZATION

Who may do what?

A deny-by-default matrix maps five roles to tables and operations, then adds row ownership and assignment checks.

RBAC
02 · CONFIDENTIALITY

In which direction?

No Read Up for reads and No Write Down for writes across five ordered classification levels.

MLS
03 · AGGREGATES

Does the set expose one?

Minimum query-set sizes, stricter MIN/MAX thresholds, and tracker history constrain statistical disclosure.

04 · MOVEMENT

Where may it go?

Downflow is blocked, and export, print, copy, save, and screenshot actions follow an explicit action policy.

05 · AT REST

Who can read it raw?

AES-256 in SQL Server, Fernet in the application layer, and salted password hashes in both paths.

CROSS-CUTTING

Who can reconstruct it?

Authentication, access decisions, writes, and role-request decisions produce audit events.

These are real code paths, not production guarantees.The demo uses public credentials and an SA database connection. The SQL Server roles and secure views do not provide a complete isolation boundary until each application user has a distinct database principal. Read the threat model before drawing production conclusions.

Model 02 · MLS

Clearance controls the direction of information.

Bell–LaPadula separates reading from writing. A subject may not read above their clearance and may not write below the classification of the data they hold.

>>> mls.check_access("Student", "GRADES", "read")
{ "allowed": False,
  "reason": "NRU Violation: clearance 1 < classification 3" }

The own-profile exception is explicit.A Student cannot read the Confidential STUDENT table generally. A dedicated view exposes only the linked student's authorised fields.

TA attendance is a documented conflict.Attendance is Secret; TA clearance is Confidential. Assignment-filtered views express the delegated duty, but a pure NRU check would deny it.

Model 03 · Inference

Small sets and narrow differences leak people.

An aggregate can reveal an individual when the population is tiny, when MIN/MAX exposes an extreme, or when two queries differ by one record.

Query-set floor

Aggregates over fewer than three records are blocked. Zero rows remain allowed because they disclose no individual.

min 3 rows

Stricter extremes

MIN and MAX require at least six records because an extreme is nearly a row-level disclosure.

min 6 rows

Tracker history

Fifty recent result-set signatures per user are compared. A symmetric difference of one is a high-risk tracker pattern.

process-local
src/security/inference_control.py
>>> inference.validate_aggregate_query(
...     "AVG", result_count=2, user_role="TA")

  "reason": "Result set size 2 is below minimum 3" }

>>> inference.track_query(

Model 04 · Flow

Upward is allowed. Downward is not.

Flow control covers both direction and action. A view may be allowed where an export is not, and a Secret clipboard context locks after use.

Upflow is allowed.Public data can be incorporated into a Secret context. The reverse is a down-classification violation.

Clipboard lock is cooperative.A screenshot block is a UI policy, not a desktop-level technical prevention.

Model 05 · Encryption

Protect the value, not just the button.

Sensitive columns are encrypted before persistence. Password storage uses a hash and per-user salt, never a reversible value.

Two key hierarchies

SQL Server uses a database master key, certificate, and AES-256 symmetric key. The application layer uses Fernet authenticated encryption with a PBKDF2-derived key.

  • SQL Server: certificate-backed AES-256 for phone, identifier, and grade values.
  • Application: Fernet, with HMAC-SHA256 authentication and PBKDF2-HMAC-SHA256 derivation.
  • Passwords: bcrypt cost 12 on the model/SQLite path; SHA-256 + salt on the SQL Server path.
  • Reveal: plaintext only through an authorised application path.
src/security/encryption.py
>>> crypto = get_encryption_manager()
>>> ciphertext = crypto.encrypt("Sensitive value")
>>> crypto.decrypt(ciphertext)
"Sensitive value"

>>> crypto.verify_password("wrong", stored_hash)
False

The published fallback key is for demonstration only.Set SRMS_MASTER_KEY for any local data you care about. The project does not implement key rotation or envelope encryption. Fernet is AES-128-CBC with HMAC-SHA256; the “AES-256” label belongs to the SQL Server symmetric key, not the Fernet primitive.

Residual risk

What the models do not solve.

Security review is more credible when the boundary is stated. These are the limitations a production design would have to address.

Published secrets

Demo accounts and the SQL Server SA password are intentionally public. They are not a credential-management design.

Split policy definitions

The Python matrix and SQL Server roles can drift. Application checks can be bypassed by a new path that calls a model directly.

Audit is mutable

AUDIT_LOG is a normal table. It is detective evidence, not an append-only or tamper-evident store.

Simulated factors

Two-factor authentication and email are demonstrations. No real TOTP provisioning or delivery exists.

Cooperative controls

Clipboard locking and screenshot blocks rely on the UI. Other applications and desktop tools are outside the boundary.

No automated regression suite

The manual test matrix is detailed, but it is not a substitute for repeatable automated security tests.
